Answer 1: deciding what to build

  • Coding agents made building 10 to 100 times faster, so product management became the slow step.
  • The fastest unit is one person who can both decide and build: an engineer who shapes product, or a PM who codes.

Ratios as Andrew Ng described them. He says to take them with a grain of salt.

Key terms

Coding agent
An AI model that can use tools, like reading files, editing code, and running commands, to complete a task. Boris Cherny's short version: a chatbot that can use tools.
Bottleneck
The slowest step in a process. It limits how fast the whole process can go.
Verification
Checking that software does what it should: tests, reviews, and other evidence you can trust.
Product management
Deciding what to build and why, based on what users need.
Developer infrastructure
The systems every change passes through: builds, tests, version control, code review, and releases.
10× (ten times)
Shorthand for an order-of-magnitude change. Speakers use it loosely, not as a precise measurement.
  • Six terms you'll meet throughout the deck
  • Coding agent
    • Cherny's definition: a chatbot that can use tools
    • The tools are what turn suggestions into actual work
  • Bottleneck
    • Speeding up a step that isn't the bottleneck doesn't speed up the whole process
  • Verification
    • Broader than tests: includes review, monitoring, and any evidence you trust
  • Product management and developer infrastructure
    • These are the two places the speakers say the bottleneck moved to
  • 10×
    • Treat it as "a lot more," not an exact figure

Software ecology and shared fate

  • Software ecology is the study of the socio-technical system that produces software: people, tools, process, and culture together.
  • Conway's law applies: organizations build systems that mirror how they communicate.
  • In Google's monorepo, shared fate means a fix in one place reaches everything. Ten well-placed lines can patch billions of lines of software.
  • That only works with a testing culture, one build platform, standard review, and transparency.
1:09 Software ecology 5:52 Shared fate 9:39 The ten-lines example
  • Software ecology defined
    • The developer environment as an ecosystem where people and technology co-evolve
    • Some properties only appear when the whole system is assembled
  • Case study: Google's monorepo
    • One repository, trunk-based development
    • A security fix in one file reaches every application within about a week
    • Ten lines in the right place can patch around ten billion lines of software
  • Shared fate is as much social as technical
    • A pervasive testing culture
    • A single build system
    • Standardized code review
    • Transparency

Worked example: why tests can grow faster than code

Plain arithmetic to illustrate Bender's general point. Not every pair needs a test, but the surface where things can interact grows much faster than the code itself.

Hiding details behind a simpler interface.

Trying hard to break a system on purpose.
API
A defined way for one program to use another's features.
Bottleneck
The slowest step, which limits the whole process.
Building blocks
Reusable pieces you combine into software.
Chatham House rule
Share what was said, not who said it.
Coding agent
An AI model that uses tools to complete coding tasks.
Continuous integration
Automatically merging and testing changes many times a day.
Conway's law
Systems mirror the communication of the teams that build them.
Dependency graph
A map of which parts depend on which others.
Deprecated
Replaced by something newer and expected to go away.
